# Benefit Hub · 平台级一级导航与配置驱动接口交付

> **2026-10-28 维护者产品决定**。覆盖此前“四个一级导航”“供应商管理仅在系统设置”的旧设计边界。本文是产品功能和交付依赖的单一决策记录，不声称功能已经上线；真实代码/数据库/接口以各自当前实现为准。

## 1. 产品不再只围绕上力转

三创的 Benefit Hub 是面向**多个上游供应商和多个下游业务应用**的权益交付中台。核心价值在于：供应商供货能力和成本；自有商品及映射；下游应用接入与权限；独立、可发布的价值换算规则；以及由这些配置生成**实际可调用**的业务接口。

**以下八项必须是一级导航**，不能把供应商、下游应用、价值换算藏在系统设置二级页面，也不能只创建一个没有能力的假入口。

| 一级导航 | 负责什么 | 第一阶段可验证的最低交付 |
| --- | --- | --- |
| **总览** | 实际业务与风险概览 | 有据可查的状态、最近更新时间；无数据不冒充零 |
| **商品管理** | 三创内部商品、只读上游目录、激活映射及冻结版本 | 真实已实现的商品与映射流程 |
| **供应商管理** | 供应商档案、环境/接入状态、能力、供货商品、成本与额度来源、关联履约 | 当前上力一家的真实档案、能力与未核实事项；不虚构第二家 |
| **下游应用** | 应用登记、服务身份、密钥状态、允许使用的商品/业务能力、调用量及关联订单 | 应用级授权、配置可查；不把后台账户当机器账户 |
| **价值换算** | 定义/预览/版本化应用与商品的价值换算预设 | 草稿→预览→校验→发布，单价/比率/单位/舍入/上限/生效期和适用范围 |
| **接口管理** | 根据已发布应用/授权/换算配置动态生成、预览、验证和发布业务 API | 可见每个应用真实有效的接口契约、地址、参数、权限、版本及停用状态 |
| **发放记录** | 本地业务订单、冻结的来源/规则与上游履约轨迹、异常核实 | 真实的本地订单与状态，不编造供应商到账 |
| **系统设置** | 后台操作员、角色、安全、系统运维 | 不承载前述核心业务管理 |

侧栏直接可见；路由、工作页签、前进后退一致；复用 Ant Design，不复制上力整个商户运营后台。此处八个一级入口与实现次序是两回事，**不得把“分期施工”解释成降级菜单层级**。

## 2. 三种业务主体与关系

- **供应商 Provider**：稳定标识、展示名称、合作与接入环境、真实可供的权益商品、能力限制、额度与成本事实。上力是目前唯一真实供应商，其 A/B/C/D 不是全平台永久枚举。
- **三创内部商品 Product**：三创自己的业务标识、定价、上下架、与特定 Provider 商品的不可变映射版本；供货来源不能替代三创商品主权。
- **下游应用 Application**：卡博士、本地生活等调用方独立登记；可授权哪些商品/能力、哪种价值预设、每单位的限额及实际调用身份。不能因为同属三创就共享所有商品、订单与余额。

应用与供应商**不直接绑定**，先经三创内部商品及已激活映射。当前的一商品单活跃映射事实不因增加应用管理而自动改为多供应商智能路由。

## 3. 价值换算预设：和供货成本、真实余额分离

规则至少包括：源价值单位（例如业务积分或其他应用自有计量单位）、目标价值/权益单位、固定值或比率、精度与舍入方式、最小/最大值与限次限制、适用应用/商品/场景、生效时间、状态与版本。业务方可以配置不同的价值体系，但**不存在默认“积分=人民币”的平台假设**。

必须有编辑、校验、即时预览、版本发布、版本历史与停用。配置以整数最小货币单位或精确十进制计算，不使用二进制浮点数拍脑袋结算；实际业务订单固定引用其创建时使用的规则版本与换算结果，版本变更不倒改老订单。

供应商的 `sellPrice`、`feeAmount`、`chargeAmount`（上力后台发现的运营字段）和三创对下游的销售定价、应用价值换算是**不同事实**。上游实际扣费须有独立订单/账本依据，不能用配置推断；礼包“份”与金额“元”分账。

## 4. 动态生成的是**可用的接口**，不是只生成一页文档

目标业务流程：

1. 登记应用并建立服务端可信调用身份。
2. 为该应用授权内部商品/能力及可见数据范围。
3. 选择或发布可用的价值换算预设及有效版本。
4. 在「接口管理」选择应用和已发布配置，**编译为受控业务 API 定义与可执行路由映射**，展示路由、请求/响应字段、鉴权、状态及错误回包、OpenAPI/调用示例。
5. 预览/验证通过后显式发布版本，应用按自己的服务凭证调用；可停用、轮换、版本升级、追踪来源及恢复历史配置。

生成层是**声明式、受限模板 + 统一安全分发器**，而不是每个项目重新硬编码一套接口，也不是允许运营人员上传 JS/SQL、拼接任意 URL 或发布无鉴权接口。对每个调用执行应用身份、商品/操作授权、版本、限额、服务端订单幂等检查；前端展示的授权不替代后端强制校验。

当前已交付的 `/api/v1/business/orders` 是固定、受保护的业务订单入站能力；新的配置驱动发布必须继承并复用这些安全原语，**不得借“动态”绕过它们**。是否采用应用命名空间、可配置 path alias 等路由形式，需独立工程合同与向后兼容验收。

**“接口已发布”与“供应商已完成发券”是不同的事实。** 是否受理、扣额、到账应来自真实履约记录，而非接口发布状态或静态禁用字段。

## 5. 错误展示与证据

维护者最新原则：**上游未知状态/原生业务码，优先保留并展示收到的原始码和安全原文；我们不自造完整的供应商错误码解释体系。** 需对任何密码、签名、完整手机号、卡密和隐私先进行服务端过滤或遮蔽。中台自己的已明确错误（例如身份未授权、商品不可用、版本冲突、订单重复但参数冲突）可以给稳定业务码；暂不能确定的原因用通用提示，不装作知道。写入超时保持“结果未知”，不能盲目再派发。

## 6. 第一轮施工顺序（可并行，不是大而全重构）

- **A：一级导航与完整页面信息架构**。八个一级入口、独立路由、页面清晰展示真实“已交付 / 未接入”，不伪造业务记录和操作成功。
- **B：供应商档案/能力读取**。从当前真实上力开始，保留环境、只读商品与费用/额度来源，未知信息明确未知；不造多供应商插件市场。
- **C：下游应用登记与受保护服务身份/授权**。复用已交付机器订单身份隔离，不修改旧合同；新的应用和商品授权持久化单独验收。
- **D：价值换算预设与发布版本**。先可复现的服务端规则求值、预览与版本快照，再接入实际订单。
- **E：配置驱动接口发布**。基于 A-D 数据定义生成**真实可调用**的受限 API、OpenAPI 契约与联调用例；先只读与本地订单意图，真实 Provider 扣额需另批。
- **F：发放记录与真实履约**。先现有本地订单；继续查 D 订单核实协议与实际成本，再经独立许可接上游派发。

验收时逐项提供“前端可点击路径→后端真实 API→权限/错误/状态→数据版本”的证据，不能以空白页面、Mock、CI 绿色代替真实业务验证。保持 `feat/* -> dev`；新一轮产品方向不自动授权合并/部署或外部扣费请求。
