## 2. 模式不可混淆的决策表

| 模式 | 前置/查询（只读业务意图） | 会产生扣额/派发副作用的请求 | 验收成功含义 |
| --- | --- | --- | --- |
| A | `POST /open/v1/prepaid/purchase-check`，`POST /open/v1/prepaid/orders/query` | `POST /open/v1/prepaid/orders`，扣 **1 个礼包** | `claimUrl` 可取回；用户可能仍需进 H5 完成领取，**不是到账** |
| B | 同 A 的 `purchase-check` | `POST /open/v1/prepaid/direct-topup`，扣 **1 个礼包** | `allClaimed` + `items`；部分失败只允许**同一 requestId** 的受控补发 |
| C | `GET /open/v1/gift-vouchers/{code}` | `POST /open/v1/gift-vouchers`，签发**立刻预扣 packCount（1–12）** | 返回兑换链接/码不等于已兑换；期限/未领取额度返还未确认 |
| D | `GET /api/open/inrice/v1/products`、`GET .../products/query`、`GET .../orders/query` | `POST .../dispatch`，扣权益**金额（元）** | `code=0` 仅受理；以查单 `dispatchStatus` 的已证实终态及 `fulfillmentSummary` 为准 |

统一 envelope `{code,message,data}`，HTTP 200 **不等于**业务成功，更不等于履约成功。A/B/C 的 `X-Sign` 为排序非空字段 + appSecret 计算 SHA-256 大写 hex，毫秒时间戳及 nonce；D 的 `X-Signature` 为 HMAC-SHA256(timestamp + "\\n" + compact JSON, secret) 的 Base64，**二者不得公用签名实现**。

## 4. 联调与安全门禁

1. 只读开发环境请求可在明确授权的测试环境进行；不得把运行时密钥放在源码、PR、Issue、日志、浏览器、GitHub 普通变量或截图。开发凭证需在服务器侧安全注入，并在公开暴露过后考虑轮换。
2. 所有真实扣额度请求先有**唯一、持久化、可重放同一业务意图**的本地标识。禁止“超时就换订单号重发”，也不能跨供应商 HTTP 调用持有 SQLite 事务。
3. A/B 的资格检查必须在收款前；C 签发本身扣额；D 必须先查单识别真实终态。礼包个数与人民币金额分账，内部货币仍使用**整数分**。
4. 上游状态不明时落 `unknown` 并人工核实；B 若 `allClaimed=false` 仍可能已扣额度；D 只用已明确的终态判断到账。
5. 需要供应商详细文档或实际观察才能冻结的内容：D 商品详情与查单 query 参数/完整终态；A/B/C 字段与错误码；C 过期和退款/额度回收；A/B 七天限领粒度；生产 URL 和真实可用测试额度。
6. CI 可用固定响应契约夹具和签名测试向量；**不得**在 PR CI 或常规构建中执行真实扣额调用。真实 dev 联调记录留脱敏证据并与模拟测试分离。
7. UI 的 `mapping validated` 仍只表示本地结构校验，不能改为“供应商已验证”。灰度/真实发放开启必须是后续独立授权，不在任何只读或映射卡的副作用里。
8. 组织 Worker 必须单卡、有界任务、Draft PR、独立验证，禁止自行合并、关卡、部署。通常一张卡能独立验证/回滚，不要把 011 与 012/013 混到一张 PR。
