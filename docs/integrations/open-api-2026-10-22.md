## 1. 先看：我们提供哪几种接入方式

按业务场景选一种即可（也可组合使用）。

| 方式 | 谁收款 | 额度扣什么 | 用户后续 | 核心接口 | 签名体系 |
|------|--------|------------|----------|----------|----------|
| **A. 预充值下单 → H5 领取** | 贵方 | 礼包个数（子分销余额 −1） | 打开 `claimUrl`，在本平台 H5 领彩票 / 点领出行券等 | `POST /open/v1/prepaid/orders` | `/open/v1`（`X-Sign`） |
| **B. 服务商直充** | 贵方 | 礼包个数（子分销余额 −1） | 无页面；接口内立刻发腾讯出行券到手机号 | `POST /open/v1/prepaid/direct-topup` | 同上 |
| **C. 公众号礼包券** | 无（免支付） | 签发时预扣 `packCount` 个 | 用户打开链接填手机号免支付领取 | `POST /open/v1/gift-vouchers` | 同上 |
| **D. 权益派发** | 贵方 | **金额（元）**，与礼包额度是两本账 | 权益发到手机号；卡密等以查单为准 | `POST /api/open/inrice/v1/dispatch` | `/api/open/inrice/v1`（`X-Signature`，算法不同） |

### 怎么选

```
贵方自己收款后调我们？
├─ 礼包要含彩票 / 出行 / 趣米，用户进我们 H5 完成领取
│     → 方式 A
├─ 礼包只有腾讯出行券，不要 H5、接口内直接发到手机号
│     → 方式 B
├─ 不收款：公众号发链接，用户填手机号免支付领
│     → 方式 C
└─ 发的是权益商品（会员卡密等），按「元」扣权益余额
      → 方式 D
```

**重要：**

- 方式 A / B / C 共用一套 AppKey，签名头是 `X-Sign`（SHA-256 大写 hex）
- 方式 D 可用同一套 AppKey，但签名头是 `X-Signature`（HMAC-SHA256 → Base64），**不要和 A/B/C 混用算法**
- 同一手机号对「免费 / 预充值礼包」有 **7 天限领 1 次**；方式 A、B 收款前务必先调 `purchase-check`

## 2. 接入准备（共用）

向平台运营确认：

| 项目 | 说明 |
|------|------|
| Base URL | 测试 / 生产，例如 `https://dev-api.isunpow.com` |
| AppKey | 请求头 `X-App-Key` |
| AppSecret | **仅服务端签名，禁止下发前端 / 小程序** |
| refCode | 子分销推广编码（方式 A/B/C 必用） |
| productCode | 礼包或权益商品编码（按方式不同） |
| 预充值余额 | 团队池下拨到子分销后，A/B/C 才能扣 |
| 权益余额 | 方式 D 按「元」扣，与礼包额度无关 |

签名与调用必须放在**贵方服务端**。支付失败 / 未支付不要调扣额度接口。

## 3. 方式 A：预充值下单 → H5 领取

### 3.1 适用

- 贵方收款成功后，扣 1 个预充值礼包额度，创建已支付订单
- 返回 `claimUrl`，用户在本平台 H5 完成：礼包确认、彩票下注、**点击领取出行券**等
- 礼包可含彩票、出行、趣米；含趣米时支付成功后会自动派发，用户在领取页查看即可

### 3.2 推荐流程

```
1) POST /open/v1/prepaid/purchase-check   ← 收款前检查（不扣额度）
2) 贵方收款成功
3) POST /open/v1/prepaid/orders          ← 扣额度 + 返回 claimUrl
4) 引导用户打开 claimUrl
5) 用户关掉页面后：POST /open/v1/prepaid/orders/query 取回原链接（不扣额度）
```

### 3.3 收款前检查

```http
POST {BASE_URL}/open/v1/prepaid/purchase-check
Content-Type: application/json
X-App-Key / X-Timestamp / X-Nonce / X-Sign
```

```json
{ "phone": "13800138000" }
```

签名字段：`appKey`、`timestamp`、`nonce`、`phone`。

| 返回字段 | 含义 | 贵方处理 |
|----------|------|----------|
| `purchaseRestricted=true` | 7 天限领中 | **不要收款、不要下单**，展示 `message` |
| `giftUnclaimed=true` | 还有非彩票权益未领完 | 把返回的 `claimUrl` 给用户继续领 |
| `lotteryUnbet=true` | 有彩票未下注 | 同上，打开 `claimUrl` |
| 三者均为 false | 可以买 | 再收款、再调下单 |

### 3.4 下单

```http
POST {BASE_URL}/open/v1/prepaid/orders
```

```json
{
  "phone": "13800138000",
  "refCode": "ref_abc123",
  "productCode": "benefit_pack_299",
  "requestId": "partner-order-20261022-0001"
}
```

| 字段 | 必填 | 说明 |
|------|:----:|------|
| phone | 是 | `^1\d{10}$` |
| refCode | 是 | 子分销推广码 |
| productCode | 否 | 省略则用平台默认礼包；也可是纯出行礼包 |
| requestId | 强烈建议 | 贵方支付单号，幂等键，最长 64 |

签名字段：`appKey`、`timestamp`、`nonce`、`phone`、`refCode`，以及非空的 `productCode` / `requestId`。

成功示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "orderNo": "PKG2026102212000001",
    "claimUrl": "https://h5.example.com/bet?orderNo=PKG...&phone=13800138000",
    "betPagePath": "/bet?orderNo=PKG...&phone=13800138000",
    "balanceAfter": 99,
    "idempotentReplay": false
  }
}
```

> **注意：** 本接口**不会自动发出行券**。用户打开 `claimUrl` 后须在 H5 **点击领取**。若只要接口内立即发券，请用方式 B。

### 3.5 再次取回领取链接

```http
POST {BASE_URL}/open/v1/prepaid/orders/query
```

```json
{ "requestId": "partner-order-20261022-0001" }
```

签名字段：`appKey`、`timestamp`、`nonce`、`requestId`。不扣额度。`claimable=true` 表示还有未完成权益。

## 4. 方式 B：服务商直充（接口内发腾讯出行券）

### 4.1 适用

- 礼包为**纯腾讯出行**（可多张、绑不同腾讯 API）
- **不能**含彩票或趣米（含了会拒绝）
- 一次调用：扣额度 → 建单 → 接口内调腾讯发券；**不返回** `claimUrl`

### 4.2 流程

```
1) POST /open/v1/prepaid/purchase-check   ← 建议收款前先查
2) 贵方收款成功
3) POST /open/v1/prepaid/direct-topup
4) 以 data.allClaimed / data.items 判断是否全部发券成功
```

### 4.3 请求

```http
POST {BASE_URL}/open/v1/prepaid/direct-topup
```

```json
{
  "phone": "13800138000",
  "refCode": "ref_abc123",
  "productCode": "travel_pack_api",
  "requestId": "partner-topup-20261022-0001"
}
```

| 字段 | 必填 | 说明 |
|------|:----:|------|
| phone | 是 | 券发到此号 |
| refCode | 是 | 子分销推广码 |
| productCode | **是** | 纯腾讯出行礼包编码 |
| requestId | 强烈建议 | 幂等；部分失败时用同一值重试可补发 |

签名字段：同方式 A 下单（`productCode` 必填，会参与签名）。

### 4.4 成功响应要点

```json
{
  "code": 0,
  "data": {
    "orderNo": "PKG...",
    "balanceAfter": 98,
    "allClaimed": true,
    "successCount": 2,
    "totalCount": 2,
    "items": [ { "claimed": true, "status": "completed", "message": "..." } ],
    "idempotentReplay": false
  }
}
```

| 判断 | 说明 |
|------|------|
| `code=0` | 仅表示扣额 / 建单流程完成 |
| `allClaimed=true` | 全部出行券发券成功 |
| `allClaimed=false` | 部分失败；额度已扣，用**同一 requestId** 再调本接口补发 |

单条发券失败平台内最多重试 3 次。

## 5. 方式 C：公众号礼包券（用户免支付）

### 5.1 适用

- 贵方公众号 / 客服发码：用户打开链接填手机号即可领，**不走微信支付**
- 签发时从子分销余额 **预扣 `packCount`**
- 微信 openid、口令表由贵方自己维护；`requestId` 可用客服口令做幂等

### 5.2 签发

```http
POST {BASE_URL}/open/v1/gift-vouchers
```

```json
{
  "refCode": "ref_abc123",
  "packCount": 3,
  "requestId": "XK92J1",
  "phone": "13800138000",
  "productCode": "benefit_pack_299"
}
```

| 字段 | 必填 | 说明 |
|------|:----:|------|
| refCode | 是 | 子分销推广码 |
| packCount | 是 | 这张券几个礼包，1～12；签发预扣等额额度 |
| requestId | 是 | 幂等键，最长 64 |
| phone | 否 | 已知才传；不传则用户在 H5 填；首次填写的号绑死该券 |
| productCode | 否 | 省略则用默认礼包 |

签名字段：`appKey`、`timestamp`、`nonce`、`refCode`、`packCount`（数字转字符串，如 `"3"`）、`requestId`，以及非空的 `phone` / `productCode`。

成功返回：`voucherCode`、`claimUrl`、`packTotal`、`packRemaining`、`expiresAt`（签发起约 30 天）、`balanceAfter`、`idempotentReplay`。

把 `claimUrl` 做成链接或二维码发给用户即可。

### 5.3 查询（补发链接用）

```http
GET {BASE_URL}/open/v1/gift-vouchers/{code}
```

签名字段：`appKey`、`timestamp`、`nonce`、`code`（须与签发返回的大写 `voucherCode` 一致）。

## 6. 方式 D：权益派发（卡密 / 会员等）

### 6.1 适用

- 派发权益商品（影视会员、卡密等），扣团队 **权益余额（元）**
- 与礼包预充值额度**不是同一本账**
- 签名算法与 A/B/C **不同**（见 §7.2）

### 6.2 流程

```
1) GET  /api/open/inrice/v1/products              ← 可派发商品列表（含 sellPrice）
2) GET  /api/open/inrice/v1/products/query?...    ← 可选，查详情
3) 贵方收款成功
4) POST /api/open/inrice/v1/dispatch              ← 按成交价扣余额并提交派发
5) GET  /api/open/inrice/v1/orders/query?...      ← 轮询至 dispatchStatus 终态
```

### 6.3 派发

```http
POST {BASE_URL}/api/open/inrice/v1/dispatch
Content-Type: application/json
X-App-Key / X-Timestamp / X-Signature
```

```json
{
  "partnerOrderNo": "P20261022001",
  "productCode": "INRICE_VIP_30",
  "mobile": "13800138000"
}
```

| 字段 | 必填 | 说明 |
|------|:----:|------|
| partnerOrderNo | 是 | 贵方业务单号，幂等键，最长 64 |
| productCode | 是 | 平台权益商品编码 |
| mobile | 是 | 领取手机号 |

`code=0` 只表示建单并已提交上游（或幂等回放），**不代表用户已到账**。请查单直到 `dispatchStatus` 为终态（如 `RECEIVE`），卡密 / 领取说明看 `fulfillmentSummary`。

同一 `partnerOrderNo` 重复调用不重复扣额。

> 更完整的字段、状态机与错误码见：[上力权益OpenAPI接口对接文档.md](./上力权益OpenAPI接口对接文档.md)

## 7. 鉴权与签名

### 7.1 方式 A / B / C（路径 `/open/v1`）

| Header | 说明 |
|--------|------|
| X-App-Key | AppKey |
| X-Timestamp | **毫秒**时间戳，偏差 ≤ 5 分钟 |
| X-Nonce | 随机串，建议每次唯一 |
| X-Sign | SHA-256 **大写** hex |

步骤：

1. 参与字段（空值不参与）按 key 字典序排序  
2. 拼成 `k1=v1&k2=v2&...&appSecret={AppSecret}`  
3. `X-Sign = UPPERCASE(SHA256(整串))`

Java 示例：

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.Map;
import java.util.TreeMap;

public static String sign(Map<String, String> params, String appSecret) throws Exception {
    TreeMap<String, String> sorted = new TreeMap<>();
    for (Map.Entry<String, String> e : params.entrySet()) {
        if (e.getValue() == null || e.getValue().isEmpty()) continue;
        if ("sign".equalsIgnoreCase(e.getKey()) || "signature".equalsIgnoreCase(e.getKey())) continue;
        sorted.put(e.getKey(), e.getValue());
    }
    StringBuilder sb = new StringBuilder();
    for (Map.Entry<String, String> e : sorted.entrySet()) {
        if (sb.length() > 0) sb.append('&');
        sb.append(e.getKey()).append('=').append(e.getValue());
    }
    sb.append("&appSecret=").append(appSecret);
    MessageDigest md = MessageDigest.getInstance("SHA-256");
    byte[] hash = md.digest(sb.toString().getBytes(StandardCharsets.UTF_8));
    StringBuilder hex = new StringBuilder(hash.length * 2);
    for (byte b : hash) hex.append(String.format("%02X", b));
    return hex.toString();
}
```

### 7.2 方式 D（路径 `/api/open/inrice/v1`）

| Header | 说明 |
|--------|------|
| X-App-Key | AppKey |
| X-Timestamp | 秒或毫秒均可 |
| X-Signature | HMAC-SHA256( `timestamp + "\n" + 紧凑JSON` , AppSecret ) → **Base64** |

**没有** `X-Nonce` / `X-Sign`。待签名 JSON 字段因接口而异（列表为 `{}`，派发为 `partnerOrderNo`/`productCode`/`mobile` 等），详见权益对接文档 §4。

## 8. 统一响应与联调清单

### 8.1 统一响应

```json
{ "code": 0, "message": "success", "data": { } }
```

| code | 含义 |
|------|------|
| 0 | 接口调用成功（直充还要再看 `allClaimed`；权益派发还要再查单） |
| 400 | 参数 / 业务失败（余额不足、限领、礼包不符等） |
| 401 | 鉴权失败 |
| 403 | 团队禁用等 |
| 500 | 服务器异常 |

业务成败以 body 的 `code` 为准，不要只看 HTTP 状态。

### 8.2 联调清单（通用）

- [ ] 已拿到 Base URL、AppKey、AppSecret；Secret 未进前端
- [ ] 时间戳为毫秒（A/B/C），时钟误差 &lt; 5 分钟
- [ ] 选对方式：A 看 `claimUrl`；B 看 `allClaimed`；D 看查单状态
- [ ] `requestId` / `partnerOrderNo` 用业务单号，验证幂等不重复扣
- [ ] **仅支付成功后**调扣额度 / 派发接口
- [ ] A/B：收款前已调 `purchase-check`，限领时不收款

## 10. 安全与联系

1. AppSecret 仅保存在贵方服务端  
2. 生产必须 HTTPS  
3. 勿将 Secret、完整签名串写入客户端或明文日志  
4. 凭证签发、额度充值、礼包 / 商品配置：联系平台运营 / 技术对接人
