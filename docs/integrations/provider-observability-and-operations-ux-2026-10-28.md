# Benefit Hub · 运营交互完整性与上力协议主动取证原则

> **维护者产品决策记录 · 2026-10-28 · 文档分支草案**
>
> 核心原则：**供应商协议可以渐进补齐，但三创自己的运营产品不能因为供应商文档不全而交互残缺。** 一切已观察的上游事实必须有证据；一切未知事实都必须被 UI 正确表达，不能用假成功、假空态或危险重试掩盖。
>
> 本文约束后续设计、排卡、实现与验收，不声称现有产品已经满足全部条款。它不替代 [第一期产品范围](../product-scope.md)、根目录 [UI 设计规范](../../design.md)、[技术架构](../architecture.md)、[2026-10-22 接口总览](./open-api-2026-10-22.md)、[接口实现与联调证据](./yangmao.md) 或各 Issue 的实施合同。**仅创建文档不授权写业务代码、真实发券/扣额、部署、合并、Issue 关闭。**

## 一、产品立场：三创平台完整，上力只是供应商

1. **Benefit Hub 是三创的平台。** 我们拥有内部商品、价格与启停、映射版本、业务订单、幂等业务意图、运营状态、权限、审计和客服/运营处理流程。上力/羊毛只是当前唯一真实 Provider；其 A/B/C/D 是上力的能力分类，不能冒充全平台永久标准。
2. **接口合同不完整 ≠ 页面只做半套。** 商品筛选、列表/卡片、详情、订单详情、进度、查询、日志、诊断、错误反馈、人工核实入口，均应按完整业务旅程设计。功能尚未开通时明确表达“未接通/待核实/当前不可操作”，而不是删除入口、做失效假按钮或拿假数据冒充成功。
3. **可演示和可运营不是同一个验收层级。** 设计稿、静态组件、Mock 流程可以用于交互验收；只有连接真实服务器、真实权限、真实可观察数据并通过相应证据门槛，才可以标示“已接入/可操作/已履约”。
4. **有证据就推进，无证据也要完整承接。** 协议未知不阻止构建通用错误抽屉、状态分区、查询轨迹、人工处理流程；但未知签名、未知终态、未知退款规则阻止真正的上游调用与自动处置。不能为了赶页面编造接口响应。
5. **完整交互不等于复杂产品。** 延续四个主导航（总览、商品管理、发放记录、系统设置）、Ant Design 6 和已有轻量架构；不借此新增第五导航、多 Provider 市场、任意重派、支付/退款中台或大规模重构。

### 各页面的最低交互完成度

| 页面/动作 | 必须覆盖的用户旅程 | 不允许的省略/误导 |
| --- | --- | --- |
| 商品管理 | 内部商品/供应商商品双 Tab；表格/卡片一致的筛选与分页；加载、空数据、错误、重试；详情与来源时间 | 切到卡片后丢失翻页、把请求失败显示为“0 个商品”、根据不明 `goodsStatus` 推出“可发放” |
| 映射与配置 | 草稿→本地校验→显式激活；版本冲突、校验失败、权限拒绝、尚未验证上游的说明；保存后状态回显 | 把 `validationScope=local` 说成供应商验证，或把映射激活等于真实发放 |
| 发放记录/详情 | 业务订单号及内部商品优先；供应商、模式、冻结映射版本、供应商单号、最近核实时间、状态轨迹；可按权限查询/核实 | 用上力原生 `dispatchStatus` 覆盖平台状态，超时后显示“失败且未扣费” |
| 异常处理 | 说明发生在哪一步、已知事实、不确定性、下一安全动作；可重新查询时提供查询；不可安全重试时提供人工核实/记录处理 | 万能“操作失败，请重试”，或给可能重复扣额的派发操作无条件一键重试 |
| 系统设置 | 供应商名称、测试/生产环境标签、接入/可读/可发能力分离、最近核验、凭证是否配置（布尔状态） | 显示 AppKey/AppSecret、原始签名或把“商品列表可读”说成“供应商发放可用” |

表格、卡片、抽屉、详情必须保持筛选与上下文、浏览器前进后退和权限一致；按现有设计基线进行 1366px 与窄屏的真人/浏览器验收。UI 组件优先复用 Ant Design，不创设第二套基础组件库。

## 二、错误必须详细、可解释、可处理，而不是只能给开发看

### 2.1 统一的错误诊断表达

不同 Provider、不同业务场景都使用**平台统一的安全诊断结构**，上力原生 code 保留为带来源的信息，而不塞进平台通用状态枚举。期望字段（**目标协议，不代表当前 API 已实现**）：

| 字段 | 用途 | 安全要求 |
| --- | --- | --- |
| `operation` / `stage` | “读取商品目录 / 发券请求 / 查询履约”等动作和失败步骤（本地校验、鉴权、供应商业务、网络、结果解析） | 固定枚举、明确中文含义 |
| `provider` / `providerMode` | 供货来源及该 Provider 的履约模式（若存在） | 不把 A/B/C/D 强制为其他供应商通用字段 |
| `internalCode` | 平台/Adapter 稳定错误码 | 可按真实类型映射解释，未知码有统一兜底 |
| `httpStatus` / `vendorCode` | HTTP 状态与上游 body 业务 code，**分别展示** | 原值必须来自真实响应，不能把 HTTP 200 标成业务成功 |
| `safeVendorMessage` | 经服务端清洗、脱敏及分类准入的上游说明（可选） | **禁止浏览器直接接收未审查的原始 message/body/HTML**；未允许时只展示安全的通用解释 |
| `requestId` / `traceId` | 平台生成的追踪号、相关业务号的脱敏安全引用 | 不等同于上游签名原文；不能泄露完整手机号、券码、token |
| `observedAt` / `lastCheckedAt` | 本次调用与最近核实时间 | 不把历史快照写成“实时状态” |
| `certainty` / `nextAction` | 结果“明确失败 / 明确受理 / 处理中 / 未知”及安全建议 | 动作权限须由**服务端业务规则**判定，不能只由前端错误码猜测 |

详细错误交互采用三层：**页面内可读的简要原因和建议动作 → 展开详情（阶段、来源、HTTP、业务码、时间、追踪号）→ 复制脱敏诊断信息**。复制内容与 UI 展示一样经过脱敏，绝不包含 Secret、签名、Cookie、认证头、完整手机号、真实卡密、上游原始响应全文或供应商富文本。

`safeVendorMessage` 是**后续应设计的功能**：服务端在确认响应可安全展示后以纯文本、长度限制、控制字符与敏感字段清理等方式输出。若无法可靠脱敏，前端仅显示内部稳定错误码与通用解释，而非“为了详细”直接透传上游 message。保留运营排障的数字码不等于展示任何上游隐私。

### 2.2 失败场景及下一动作

| 观测事实 | 页面表达 | 下一安全动作 |
| --- | --- | --- |
| 未配置/配置缺失 | 供应商连接尚未配置，当前无法查询 | 有权限人员检查服务端配置；不显示密钥 |
| 401/403（HTTP 或上游业务 body） | 鉴权失败或供应商拒绝；显示是 HTTP 码还是业务码 | 检查授权、凭证、时间戳与签名；不自动触发写操作 |
| 供应商返回 `code!=0` | 真实业务失败，保留上游数字码及安全说明 | 根据可核实规则指导运营；未知错误进入人工核实 |
| 成功 HTTP + 非法/缺字段响应 | 上游返回结构与当前已确认合同不一致 | 保存非敏感结构线索、提供追踪编号并报告协议漂移 |
| 只读查询超时/网络失败 | 无法获得本次查询结果，不等于查得空数据 | 安全的只读查询可按节流规则重试 |
| 写入类发放超时/断连 | **结果未知，可能已扣额、已受理或已派发** | 固定原业务意图，优先查单/对账；不换 `requestId`/`partnerOrderNo` 再发 |
| B `allClaimed=false` | 直充存在部分未完成；绝不能当整体成功 | 核实 item 明细；仅在原 `requestId`、供应商许可和权限具备时受控补发 |
| A 返回领取链接 | 订单/链接可用但用户仍可能未领取 | 显示待领取与继续领取路径，绝不标记已到账 |
| C 兑换链接/码已签发 | 已签发且预扣礼包额度，不等于用户已核销 | 展示已知剩余/有效期，未核定的退额规则明确“未知” |
| D `code=0` / 未核实的 `dispatchStatus` | 受理不等于履约，未知状态保持 `unknown` | 依据已确认查单协议核实；无证据时人工处理 |

严禁把不确定的供应商原生状态直接映射为平台 `completed`、`failed`、`refunded`；也不允许通过 UI 文案掩盖真实发放开关 `vendorFulfillmentEnabled=false`。

### 2.3 前端交付的验收案例

每个真实页面至少能判定：首屏加载、成功数据、真实空态、鉴权失败、无权限、配置缺失、上游业务错误、网络超时/断连、格式漂移、重试/重新查询、详情关闭后筛选与分页保留、窄屏正常使用。订单/发放类页面额外验证“上游处理中”“部分成功”“结果未知”及**禁止危险重试**。模拟场景必须明确标注模拟，不能拿 Mock 充当线上供应商联调。

## 三、我们可以主动侦测上力的**可观察协议**，但不编造“完整协议”

**主动取证不是被动等供应商写完说明书。** 已授权测试环境 + 凭证 + 只读行为 + 真实页面/脚本 + 结构化响应，可以逐步核定**实际可观察到的**参数、签名输入、响应类型、字段、错误码和状态转移。结论逐条记录，不一次性把单个样本推广成“完整合同”。

### 3.1 证据分级与实施门槛

| 级别 | 证据来源 | 允许据此宣称 |
| --- | --- | --- |
| E0 待查 | 路径名、猜测、UI 字段名、接口命名 | 仅列调查假设，不能实现为已证实合同 |
| E1 文档明示 | 厂商总览/细文档明确给出的字段、算法、枚举及版本 | “文档规定”，尚不代表当前测试环境实际接受 |
| E2 实测观察 | 授权测试环境中受控的真实 HTTP 响应；记录请求方法、已脱敏参数/签名 JSON 结构、HTTP/body code、返回字段类型、日期 | “在该条件下已实测”，**不代表所有边界、全部错误码、所有终态** |
| E3 独立代码契约 | 固定测试向量、真实客户端、异常分支、网络隔离测试及精确代码版本 | “当前实现符合已知合同”，不证明真实环境发放可用 |
| E4 完整业务闭环 | 经单独授权的合法业务场景、真实幂等/查单/履约/额度证据 | “该业务情境已验收”，不能把其他模式或环境顺带宣称完成 |

**同一协议可能同时具备 E1/E2/E3，不是用最高等级抹掉其他缺口。** 技术实现、页面可访问、供应商鉴权、真实履约、生产部署分别留证据，不能跨层冒领成功。

### 3.2 受控主动发现方法

1. **从原文与当前代码出发**：优先读取总览、已有 Adapter、Issue 记录、环境版本，整理方法/路径/已知参数；避免重复以前失败的猜测。
2. **读取上力后台可见的真实页面与公开静态脚本**：能够确认管理端存在什么页面、有哪些展示字段、如何做后台列表与详情；但 `/admin/inrice/orders` 等**后台管理 API 不等于签名 Open API**，不能将其参数、权限、响应直接移植到 `/api/open/inrice/v1/orders/query`。
3. **最小化授权只读 HTTP 取证**：优先 GET 商品列表/详情/已知订单查单；对 HTTP 方法虽为 POST 但业务意图只读的 `purchase-check`、`orders/query`，也需按授权测试身份和无副作用合同核实后执行；使用固定额度与速率、明示请求上限，不做高频枚举或未批准的身份/订单探测。
4. **记录每个样本的边界**：脱敏记录请求方法、路径、query key、参与签名 JSON 的**字段名及类型**、HTTP 状态、body code、`data` 类型、已观察字段类型、时间、开发环境、是否独立复现。原始密钥、签名、真实手机号、卡密、可识别订单及完整响应不进入公共 GitHub。
5. **以失败类型缩小差异**：将“HTTP 不通、鉴权错误、验签失败、业务参数错误、订单不存在、处理中”分开。单一 401 不能证明字段不存在；只有得到可解释的有效回包或厂家确认，才能核定 query 与签名合同。
6. **显式定义终止条件**：缺授权数据、连续猜测无信息增益、触发限流/风控或结果可能涉真实用户时立即停止。不要为获得“全协议”而绕过账户权限、扫描私有接口、批量碰撞真实订单或调用扣额接口。
7. **取证闭环**：E2 新事实先与仓库现有合同/测试对照，再回写 `docs/integrations/yangmao.md` 的事实台账及对应 Issue，新增固定脱敏契约夹具、错误码映射与真实 UI 验收。修订工作要有明确授权和原子任务，不因为“调查成功”自动合并/发布。

### 3.3 截至 2026-10-28 的 10 条接口认知矩阵

以下“实测”仅指**开发环境的已观察事实**；未写“实测”的项目不能据概念/示例推定有真实鉴权成功。

| 模式 | 方法与路径 | 已掌握 | 尚缺/禁止推断 |
| --- | --- | --- | --- |
| A/B | POST `/open/v1/prepaid/purchase-check` | E1 请求 `phone`、A/B/C `X-Sign` 签名字段；E3 已有隔离测试客户端；**业务意图只读** | 无已成功签名的 E2 资格响应；七天限领实际作用范围未知；需合法测试手机号 |
| A | POST `/open/v1/prepaid/orders` | E1 `phone/refCode/productCode?/requestId?`，扣 1 个礼包、返 `claimUrl` | 扣额写接口，未获真实发放授权，禁止联调调用；到账并非该操作成功的同义词 |
| A | POST `/open/v1/prepaid/orders/query` | E1 按 `requestId` 查询领取链接，业务意图只读 | 需授权的**已有**订单号和签名验证，不能造单 |
| B | POST `/open/v1/prepaid/direct-topup` | E1 `phone/refCode/productCode/requestId`；`allClaimed` 与 `items` 决定结果 | 扣礼包并触发发券；不得为摸错误码而调用 |
| C | POST `/open/v1/gift-vouchers` | E1 `refCode/packCount/requestId/phone?/productCode?`，签发即预扣 1–12 个礼包 | 扣额写接口，未验证；到期剩余额度是否退回未知 |
| C | GET `/open/v1/gift-vouchers/{code}` | E1 签名含实际券码 `code`；业务意图只读 | 需要已有、获授权的券码；无真实 E2 样本 |
| D | GET `/api/open/inrice/v1/products` | **E2** 2026-10-28 真实 `X-Signature` 验证：HTTP 200、body `code=0`、`data` 为 21 项数组；21 个 `productCode` 非空且不重复，`sellPrice` 本轮均符合现有分价精度校验；E3 有 Adapter 测试 | 不等于商品可售、额度可用或成功发券 |
| D | GET `/api/open/inrice/v1/products/query` | **E2** 2026-10-28 真实 `productCode` query 与同字段紧凑 JSON HMAC 签名成功，HTTP 200、`code=0`、`data` 对象且编码回显一致；现有详情有 `name/sellPrice` 等字段；E3 有 Adapter | `goodsStatus` 枚举/可售意义、富文本/卡密安全语义尚未确认 |
| D | POST `/api/open/inrice/v1/dispatch` | E1 `partnerOrderNo/productCode/mobile`；金额账本，`code=0` 仅受理 | **有扣余额与发放副作用**；无授权不得调用，更不能用以生成查单测试订单 |
| D | GET `/api/open/inrice/v1/orders/query` | E1 只有路径、查询结果会涉及 `dispatchStatus/fulfillmentSummary`；2026-10-27 E2 **负例**：空签名载荷与 `partnerOrderNo/orderNo/thirdPartyNo/recordNo/inriceRecordNo` 几种同名签名猜测均得到 HTTP 200、body `code=401`“Open API 验签失败” | **仍未知准确 query key、待签名 JSON、有效响应结构与完整终态/退款集合**；负例不能定性为“正确字段无效” |

两套签名**严格隔离**：A/B/C 使用 `X-App-Key`、毫秒 `X-Timestamp`、`X-Nonce`、按非空字段排序拼接 Secret 的 `X-Sign`（SHA-256 大写 hex）；D 使用 `X-App-Key`、`X-Timestamp`、`X-Signature`（Base64 HMAC-SHA256，签名输入为 timestamp + 换行 + 紧凑 JSON）。开发环境可共用已获授权凭证，但这**不是** A/B/C 真实联调通过的证据。

### 3.4 继续调查最有价值的缺口

**P0 — D 查单**：准确 URL query 字段和签名 JSON 字段集；获授权的已有测试订单只读样本；`data` 结构；完整 `dispatchStatus`、终态、失败/退款/部分完成、`fulfillmentSummary` 的安全展示规则。历史五种负例已做过，**不重复无界穷举**。优先争取供应商有效请求示例或已授权后台可见的 D 测试订单。

**P1 — A/B/C 的只读合同**：安全测试手机号上的 `purchase-check` 真实资格响应；已有 A 订单的链接取回；已有 C 券码的详情查询；认证/业务错误码与七天限领的适用粒度。

**P1 — 资金与恢复**：两套余额的正式查询接口是否存在，C 未领到期退额、D 失败退款/撤销、上游限流及错误恢复语义。**总览中未列出的接口只能标“待核实是否存在”，不能假造余额 API。**

**P2 — 跨场景覆盖**：真实空态、配置未就绪、查询被拒、格式变化、网络与登录失效时前端如何恢复，以及同一 Provider 的多环境差异。

## 四、落实到未来卡片的验收规则

1. **UI 卡片**：先给完整状态图/交互清单，覆盖 loading、empty、error、unknown、retry、保留筛选与分页、权限和窄屏；无真实能力时须安全禁用或解释，不许仅凭“接口已存在”就验收页面。
2. **Adapter 卡片**：附已确认 E1/E2 协议字段与 E3 测试；要证明签名输入、HTTP/body 双层判断、解析、超时、鉴权、未知字段、来源与时间，不许“根据示例猜全部终态”。
3. **业务发放卡片**：单独授权真实外部副作用；固定唯一业务号与映射版本，先落库业务意图，审计每次尝试；网络未知保留 unknown，除可证明受控幂等/查单外不得自动补发。
4. **错误可观测性卡片**：从服务端到 UI 一条线验收；真实失败可在页面清楚说出“哪个阶段、哪层 code、已知结果、下一步”。需同时测“安全消息足够有用”与“绝不泄露密钥/个人信息”。
5. **证据归属**：Issue 负责目标与验收合同；`yangmao.md` 是供应商协议**已知事实与联调记录**；本文是长期产品/取证原则；根 `design.md` 负责实际视觉交互；代码/测试负责实现事实。不要将同一事实各自维护为多个会漂移的版本。
6. **执行与发布**：遵循 `feat/* -> dev`；文档分支不能被当作实现完成。后续 PR/CI/真人浏览器验收/实际部署必须各自独立确认，禁止未经授权合并、上线或关闭任务。
