## 1. 产品定位

Benefit Hub 是三创可复用的**权益供应服务**，不是某个业务的活动页面，也不是一期就要建成的集团积分中台。第一期两块：

1. **服务适配层**：对不同权益供应商进行协议适配，向三创业务暴露统一、安全、可靠的权益服务；首家上力提供 A/B/C/D 四种模式，**但这不是平台对所有供应商的永久标准分类**。
2. **运营业务层**：运营人员管理自有商品、供应商、履约记录与异常、应用授权和价值规则。
3. **下游接口交付层（2026-10-28 新增）**：根据应用权限和已发布价值换算预设形成可用、可控、版本化的动态业务接口；不是每个应用另写一套后端，也不是只生成文档。

首个供应商是羊毛系统。面向卡博士、本地生活、核心产业学院、见趣等公司业务提供可复用的供应能力，**不预设哪个业务最先上线**；实际接入入口、积分兑换或奖励规则仍由各业务独立决策，**不在第一期替这些产品擅自上线入口**。

## 1A. 平台主体与供应商规则继承（2026-10-27 补充共识）

**三创 Benefit Hub 是产品及业务规则的主人；上力是首家、目前唯一已接入联调的权益供应商，不是平台本体。** 对未来供应商开放接入可能性不意味着一期要建设插件市场、多租户系统或全套供应商管理引擎。

- **平台拥有、供应商必须遵守的共同基线**：三创内部商品编码/上下架、业务来源与订单号、不可重复扣发的幂等业务意图、可信履约状态、失败与未知区分、操作授权与审计、固定订单映射版本、敏感数据保护、可追溯成本/扣减事实。无论哪个提供商履约，不能因为它“API 调用成功”就绕开这些约束。
- **供应商拥有、只在该供应商下解释的规则**：对接地址和鉴权算法、原始商品与供货价、可提供的商品/能力、领取限制、额度种类与扣减点、请求字段、上游状态码、查单与恢复协议；例如上力的七天限领、A/B/C/D 编码、礼包余额与权益金额账本。
- **继承不是覆盖**：先由 Benefit Hub 校验通用安全与业务约束，再由所选供应商 Adapter 施加自身能力和更严格的限制。若所选供应商不支持某项业务能力，应明确拒绝/标记不可用，不能通过改写平台规则、换供应商单号或伪造成功绕过。
- **接口统一而事实不抹平**：下游只需本平台商品、业务身份、统一状态和允许暴露的领取信息；内部仍保存“由哪个供应商、该次实际使用的 provider mode / 产品编码 / 幂等引用 / 额度单位 / 映射快照”以便核实。抽象层不能消除 C 签发即扣额、D 查单才能证实履约等真实差异。
- **运营独立**：内部商品可配置展示、定价、上下架与映射版本；供应商商品是各 Provider 的**只读供货目录**，其名称、报价、可用性只按来源及查询时间展示。供应商价格不会自动覆盖我们的展示价格。
- **一期轻量性**：只交付首个上力 Adapter 和当前必要的 provider 标识、能力适配和界面供应商归属信息。不因为“以后可能有第二家”新建通用插件加载器、抽象工厂、动态路由、跨供应商智能比价/自动切换、通用结算或一键改供应商机制。

上力供应商 A/B/C/D 对应的具体合同见下表，但这张表应被理解为 **Provider: 上力的能力示例**，而不是平台永久的四种固定履约方式。已有 `fulfillmentMode` 的持久化/公共 DTO 目前包含 A/B/C/D，属于已经落地的一期兼容事实；改成 provider-scoped mode 或引入平台归一化 capability 类型必须另行设计和迁移验收，**不能在 011 的只读卡里重构**。

## 2. 面向内部业务的能力

| 场景 | 服务能力 | 体验预期 | 特殊边界 |
| --- | --- | --- | --- |
| A：预充值礼包下单 | 前置购买资格检查、已收款业务订单创建、领取链接查询 | 用户打开供应商 H5 完成领取 | 收款属于业务方；创建订单后不代表出行券已自动发放 |
| B：腾讯出行券直充 | 前置资格检查、按手机号直接发券、明细与补发结果 | 无需跳 H5；显示实际到账进度 | 仅纯腾讯出行商品，支持原幂等键对部分失败补发 |
| C：免费礼包券 | 签发兑换码/链接、查询恢复 | 运营发链接，用户可填手机号领取 | 签发即预扣礼包额度；券到期处理需向上游确认 |
| D：权益商品派发 | 查询商品/派发/查单，归一化状态 | 手机号领取卡密/会员等 | 扣的是权益金额余额，终态以查询为准 |

对其他业务只暴露我们的**内部商品编号、业务订单号、可审计的状态与操作权限**，不暴露上游 AppSecret、签名字段或内部扣费细节。

### 第一阶段调用方限制

- 不实现代收款；A/B/D 只有在业务方确认符合其支付/发奖条件后才调用会产生额度扣减的接口。
- 收款前对 A/B 调供应商 `purchase-check`，受限则不让业务方继续收款流程。
- C 不走支付，但签发时就产生额度成本；必须被授权、计入发行记录。
- 支持重复请求返回同一业务意图结果或继续核实，绝不通过换订单号掩盖未知结果。
- 发放完成不是“接口请求返回成功”；真实履约需要逐模式判定。

## 3. 轻量运营后台

**2026-10-28 更新：八个一级业务导航，取代原四页约束。** 新平台骨架与配置生成接口的完整业务合同见 [平台一级导航与配置驱动接口决策](./platform-config-and-api-delivery-2026-10-28.md)。仍优先用 Ant Design 满足运营效率。

| 页面 | 最小功能 | 不做什么 |
| --- | --- | --- |
| **总览** | 今日订单/发放数，实际成功/待处理/异常数，最近一次已知额度快照与时间戳 | 没有上游余额接口时不伪称实时余额 |
| **商品管理** | 我们自己的权益商品、供应商商品编码映射、发放模式、启停、展示及成本/定价设置 | 不假设可以修改羊毛商品或其平台成本 |
| **供应商管理** | 供应商档案、环境/能力与接入状态、供货目录、成本和额度来源、关联履约 | 不把上力管理员 API 当作通用 Open API，不造第二家假供应商 |
| **下游应用** | 应用身份、服务凭证状态、授权商品/操作、配额、接入记录 | 不把后台运营身份当服务身份，不允许跨应用读写 |
| **价值换算** | 按应用与商品的单位/比率或固定值、精度舍入、限额、生效期与版本化预设 | 不默认等值转换，不把价值换算当实际供应商扣额 |
| **接口管理** | 根据已发布的应用授权和换算规则动态生成可调用的受控接口定义、预览、发布/停用和调用示例 | 不产生任意可执行脚本、不绕过已存在机器接口鉴权 |
| **发放记录** | 按时间、业务来源、业务单号、手机号脱敏筛选；看详情/上游响应摘要/处理状态；按规则核实或受控重试 | 不提供“一键任意重发”、不允许手动改为成功 |
| **系统设置** | 运营账号、安全与平台运维配置 | 不再承载供应商管理或下游价值规则 |

账号密码登录。敏感操作需要管理权限并记录操作人、时间、关联单号、动作与结果；不展示完整密钥或敏感发放凭证。

### 运营流程原则

- 失败分成**可以明确重试**与**上游结果未知待核实**；页面提示两者的不同处理路径。
- B 模式部分失败可按供应商规则使用**同一个** `requestId` 补发。D 先查单，不自行猜测状态或产生重复派发。
- 运营人员查看订单详情能知道“是否扣额”“是否提交”“用户是否需主动领取”“为何未完成”。
- 各业务使用同一个权益中心不代表统一共享额度池；账户及额度归属按供应商凭证/refCode 实际配置。

### 已冻结的商品与映射行为（2026-10-22）

以下是**产品业务规则**，具体视觉交互只在根目录 [design.md](../design.md) 定义。

- 商品管理区分两类实体：**内部商品**由本平台管理名称、展示、启停和运营价格；**供应商商品**来自上游商品目录，默认只读。供应商没有开放修改 API 的字段，不能在本平台伪装成可编辑。
- 后台商品管理使用**内部商品 / 供应商商品两个 Tab**，并支持表格/卡片视图切换；筛选、操作入口和权限在两种视图下一致。
- **一个内部商品同一时间最多有一条生效的供应商履约映射**；关联供应商、上游 productCode、A/B/C/D 模式、扣减单位等信息。未来组合多件权益的“组合商品”不纳入本期映射模型。
- **映射编辑分为保存草稿 → 校验 → 显式激活**，不加人工审批；草稿不改变当前履约映射，修改核心字段后须重新校验。校验必须区分本地规则与上游真实验证，缺乏上游实证时不能声称已验证通过。
- 激活会生成新的生效版本并留存操作者、时间、配置及变更记录。旧版本只读；恢复旧配置也必须以它为基础生成新草稿，经校验再激活。**已经创建的订单持续关联它创建时的映射版本**，不能显示成新版本。
- 商品启停与映射生效分别管理。停用商品不删除映射历史，映射切换也不能悄悄重写已存在的履约订单。
- 第一阶段后台访问**先登录**：首次访问是品牌封面 + 登录框，没有免登录只读工作台。运营账号分为只读查看与管理员两种最简权限；敏感变更由服务端鉴权并审计，不建设复杂 RBAC/审批流。

## 4. 首期不做

不建设付款/退款中台、复杂库存/积分清算平台、抽奖与组队营销引擎、供应商余额充值、自动创建供应商商品、多租户组织/审批流、移动端专用 App。**下游应用、价值换算和动态业务接口发布属于本平台核心工作，不等于复杂积分清算平台或自动选商/比价系统。**未来需求另做产品决策，不在首期工程里预埋大量占位模块。

## 5. 第一阶段可验收结果（不是实施卡）

1. **真实 API 路径可用**：业务侧用本平台业务单号访问权益接口，服务端安全签名，供应商仅能看到被授权数据。
2. **四种模式可分别验收**：模拟环境通过合同/异常测试，真实联调需有供应商测试资格与结果证据；未拿到凭证不得声称真实发放。
3. **状态可信**：B 部分成功、D 处理中、A 待用户领取、C 过期等都能表达，不造假成功。
4. **重复调用不重复扣额**：并发/超时/重试有可核验记录；依赖上游幂等语义的路径需用对应环境验证。
5. **后台可运营**：账号密码登录，商品映射配置，记录筛选与详情，异常处理日志。
6. **数据可保留**：容器重建不会删除订单与数据库；备份/恢复和升级回滚策略有验证证据。
7. **发布可验证**：经批准的 `dev` 构建部署到新服务器，应用与既有原型服务互不干扰，HTTPS 健康检查和基础运营页面真实可访问。
