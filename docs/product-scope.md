## 1. 产品定位

Benefit Hub 的**目标形态**是三创可复用的权益供应服务，但目前按**系统级原型**建设：用于完整展示服务适配、订单履约、运营管理的交互与架构，不供真实用户使用，也不直接承担生产权益发放。它不是某个业务的活动页面，也不是一期就要建成的集团积分中台。原型范围仍保留两块：

1. **服务适配层**：封装羊毛系统的四种能力，对我们的业务暴露统一、安全、可靠的权益发放服务。
2. **轻量运营层**：让运营人员配置我们提供的权益商品、查看发放与额度快照、处理异常、管理连接设置。

首个供应商是羊毛系统。先支持本地生活等公司业务接入，后续卡博士/活动/积分商城是否启用属于各自业务决策，**不在第一期替这些产品擅自上线入口**。

## 2. 面向内部业务的能力

| 场景 | 服务能力 | 体验预期 | 特殊边界 |
| --- | --- | --- | --- |
| A：预充值礼包下单 | 前置购买资格检查、已收款业务订单创建、领取链接查询 | 用户打开供应商 H5 完成领取 | 收款属于业务方；创建订单后不代表出行券已自动发放 |
| B：腾讯出行券直充 | 前置资格检查、按手机号直接发券、明细与补发结果 | 无需跳 H5；显示实际到账进度 | 仅纯腾讯出行商品，支持原幂等键对部分失败补发 |
| C：免费礼包券 | 签发兑换码/链接、查询恢复 | 运营发链接，用户可填手机号领取 | 签发即预扣礼包额度；券到期处理需向上游确认 |
| D：权益商品派发 | 查询商品/派发/查单，归一化状态 | 手机号领取卡密/会员等 | 扣的是权益金额余额，终态以查询为准 |

对其他业务只暴露我们的**内部商品编号、业务订单号、可审计的状态与操作权限**，不暴露上游 AppSecret、签名字段或内部扣费细节。

### 第一阶段调用方限制

- 不实现代收款；A/B/D 只有在业务方确认符合其支付/发奖条件后才调用会产生额度扣减的接口。
- 收款前对 A/B 调供应商 `purchase-check`，受限则不让业务方继续收款流程。
- C 不走支付，但签发时就产生额度成本；必须被授权、计入发行记录。
- 支持重复请求返回同一业务意图结果或继续核实，绝不通过换订单号掩盖未知结果。
- 发放完成不是“接口请求返回成功”；真实履约需要逐模式判定。

## 3. 轻量运营后台

初期四个导航页面，优先用成熟 Ant Design 组件满足运营效率。

| 页面 | 最小功能 | 不做什么 |
| --- | --- | --- |
| **总览** | 今日订单/发放数，实际成功/待处理/异常数，最近一次已知额度快照与时间戳 | 没有上游余额接口时不伪称实时余额 |
| **商品管理** | 我们自己的权益商品、供应商商品编码映射、发放模式、启停、展示及成本/定价设置 | 不假设可以修改羊毛商品或其平台成本 |
| **发放记录** | 按时间、业务来源、业务单号、手机号脱敏筛选；看详情/上游响应摘要/处理状态；按规则核实或受控重试 | 不提供“一键任意重发”、不允许手动改为成功 |
| **系统设置** | 供应商环境、凭证配置/状态、refCode、运营账号与基础操作日志入口 | 不做复杂团队角色矩阵、SSO、余额充值后台 |

账号密码登录。敏感操作需要管理权限并记录操作人、时间、关联单号、动作与结果；不展示完整密钥或敏感发放凭证。

### 运营流程原则

- 失败分成**可以明确重试**与**上游结果未知待核实**；页面提示两者的不同处理路径。
- B 模式部分失败可按供应商规则使用**同一个** `requestId` 补发。D 先查单，不自行猜测状态或产生重复派发。
- 运营人员查看订单详情能知道“是否扣额”“是否提交”“用户是否需主动领取”“为何未完成”。
- 各业务使用同一个权益中心不代表统一共享额度池；账户及额度归属按供应商凭证/refCode 实际配置。

## 4. 首期不做

不建设付款/退款中台、复杂库存/积分清算平台、抽奖与组队营销引擎、供应商余额充值、自动创建供应商商品、多租户组织/审批流、移动端专用 App。未来需求另做产品决策，不在首期工程里预埋大量占位模块。

## 5. 第一阶段原型可验收结果（不是实施卡）

原型验收分为模拟/沙箱行为与独立授权的真实对接试验；**公开展示的系统不默认具有生产发放权限**。模拟数据必须显式可辨，不得对真实手机号、真实额度或真实卡密执行无授权的发放。

1. **平台 API 契约可演示**：业务侧用本平台业务单号访问内部接口；模拟/沙箱供应商返回的签名、幂等与错误语义可验证。真实第三方联调另需测试凭证和明确授权，不纳入公共演示默认能力。
2. **四种模式可分别验收**：模拟环境通过合同/异常测试，真实联调需有供应商测试资格与结果证据；未拿到凭证不得声称真实发放。
3. **状态可信**：B 部分成功、D 处理中、A 待用户领取、C 过期等都能表达，不造假成功。
4. **重复调用不重复扣额**：并发/超时/重试有可核验记录；依赖上游幂等语义的路径需用对应环境验证。
5. **后台可运营**：账号密码登录，商品映射配置，记录筛选与详情，异常处理日志。
6. **数据可保留**：容器重建不会删除订单与数据库；备份/恢复和升级回滚策略有验证证据。
7. **发布可验证**：经批准的 `dev` 构建部署到新服务器，应用与既有原型服务互不干扰，HTTPS 健康检查和基础运营页面真实可访问。

## 6. 联调与产品待明确事项

- 厂商测试/生产 Base URL、密钥、子分销编码、可用商品及额度账户。
- 供应商限制：7 天限领是否跨商品/跨业务共享，C 过期未领是否退回额度，活动场景与限领规则冲突的处理。
- C 礼券发放给已知手机号还是匿名领取链接，后台权限与防滥发措施。
- 下游业务方的鉴权方式、调用限额、回调还是查询为主（现有上游总览以查询为主）。
- 四个页面的最终视觉方案、产品文案与体验细节（待在 `design.md` 讨论）。
