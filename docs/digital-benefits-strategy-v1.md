# 三创数字中台｜数字权益模块业务战略 V1

> **结论日期**：2026-10-23  
> **状态**：业务战略已收口；本文件不是研发实施授权、数据库设计或上线验收记录。  
> **归属**：三创数字中台（用户、积分、数字权益三大能力中的**数字权益模块**）。  
> **存放说明**：暂存于 `sanchuang-dev/benefit-hub` 作为其**上层业务背景和能力边界参考**；不能据此把 Benefit Hub 第一期扩大为完整权益中台。Benefit Hub 当前实施范围仍以 [product-scope.md](./product-scope.md) 为准。

## 1. 一句话定位

**三创统一定义权益、记录用户持有及权益履约事实，业务渠道负责激励和运营，供应商负责真实供给与交付。**

要掌握的是权益目录、用户归属、履约记录、实际成本和跨业务使用的可验证关系，不是先建一个庞大的 CRM、积分清算或营销运营平台。

设计原则：**高内聚、低耦合、轻量化；业务模块自治，优先 API；逻辑模块不强制拆成微服务；不为假设中的远期需求提前建设复杂工程。**

## 2. 在三创数字中台中的位置

| 边界 | 负责 | 不负责 |
| --- | --- | --- |
| 用户能力（相邻模块） | 稳定用户标识、现有业务身份关联，提供具备合理依据的用户映射 | 数字权益模块不取代各业务登录，也不负责全量用户画像 |
| 积分能力（相邻模块） | 各种积分的账户、增减及幂等；可作为获取权益的条件或支付手段 | 数字权益模块不决定泡泡值/学力值汇率，不要求发权益前必经积分 |
| **数字权益模块（本文）** | 统一商品目录、用户权益账户、发放/使用记录、履约状态、成本及额度事实 | 不决定活动玩法，不经营下游的广告、课程、签到、组队规则 |
| **Benefit Hub（现有仓库）** | 供应商商品映射、供应商调用/订单、幂等、履约查询、采购额度与成本事实，轻量运营 | **不等于完整数字权益模块**；其第一期不承担中台统一用户权益账户与跨业务权益治理的全部职责 |
| 下游业务渠道 | 何时、向谁、以何种条件奖励；页面呈现及活动经营；提供必要的收入/效果数据 | 不自行篡改中台权益归属、履约及成本记录 |

适用业务：卡博士、核心产业学院、见趣、本地生活，以及未来的独立羊毛 App/小程序。**业务共享中台能力，不等于共享所有用户数据或自动互用预算。**

## 3. V1 的六项产品能力（目标边界，非一次性交付清单）

1. **统一权益目录**：内部定义权益商品、用户承诺、适用场景和生效规则；内部商品 ID 独立于供应商 SKU。一项权益可按商品承诺对应多个合格供给来源，但首期不做复杂自动选路。
2. **统一用户权益账户**：为确认关联的用户记录具体持有权益实例、来源业务/活动、有效期、状态及必要的履约引用；不必建设统一卡包前端。
3. **权益发放与使用**：接受业务基于积分兑换、广告激励、活动赠送、直接领取等路径的发放请求；业务判断奖励资格，中台保证发放意图与结果可追踪、避免重复。
4. **跨业务使用**：权益默认具有跨业务展示和使用能力；具体权益可以限制业务、入口、区域、时段、对象和履约条件。
5. **供应履约与异常处理**：建立内部业务订单/履约事实，查询实际交付结果；失败、部分完成、处理中、结果未知要能区分。
6. **成本及额度控制**：记录成本承担业务/活动、供应商实际扣额/采购成本及有效预算约束；业务预算与公共福利池分开管理。

其中「用户权益账户」是**轻量归属账本**：既可表示待使用凭证，也可表示已经完成直充/即时兑现的权益记录。**不能把所有权益强行视为未核销券码**；三创持有的权利记录也不等于对第三方服务拥有无限制法律所有权。

## 4. 最小业务对象和关系

| 对象 | 核心含义 |
| --- | --- |
| 三创权益商品 | 下游看到的产品定义及可兑现承诺，独立于供应商命名和商品 ID |
| 供应商商品映射 | 供应商 SKU、供给方式、适用限制、价格及可供给状态 |
| 用户权益实例 | 某用户实际获得的一份权益、来源业务/活动、有效期、使用权限及当前状态 |
| 发放/使用业务记录 | 业务请求、业务单号、资格与预算归属，形成幂等及审计依据 |
| 供应商履约订单 | 调用上游的订单及明细、扣额、查单结果、最终实际交付结果 |
| 额度与成本事实 | 哪个活动/业务承担成本、预算占用、实际扣减与可确认的退回/冲正 |

**统一商品 ≠ 供应商 SKU ≠ 用户持有的一份权益。** 一项三创权益可以更换合格供应商，但必须满足相同用户承诺；不能仅凭名称相似认定可替代。

## 5. 已确定的流转与运营原则

### 5.1 跨业务使用与用户之间转赠严格区分

- **已确定：** 用户在见趣获得的合格权益，可从卡博士等其他授权业务入口查看/使用；具体权益自行限制适用场景。
- **已确定：** 领取渠道与使用渠道不必相同；单次核销应反映为统一状态，不因切换入口产生重复兑现。
- **已确定：** 用户之间是否可转赠及规则，由**下游渠道在其同一价值体系中决定**；中台当前只保留未来受控变更归属及可追溯的扩展边界，不实现通用转赠市场或兑换交易。
- **已确定：** 跨业务使用**不自动转移成本承担责任**。见趣活动承担的权益成本，不因用户从卡博士入口使用就自动变为卡博士成本。
- **必要边界：** 跨业务识别、展示或使用须建立在适当的身份关联、权限及数据授权基础上，不能以同手机号字符串直接视为已确认自然人。

### 5.2 成本池与活动授权

- **混合成本归属：** 统一资源采购能力之下，业务独立成本池与三创公共福利池并存。
- **公共福利池只能显式、按活动授权**：每次授权限定业务/活动、权益范围、预算上限及有效期。
- **业务预算耗尽不自动使用公共福利池兜底**；无有效授权不得透支发放。
- 广告收入、积分增减、权益成本是不同经营事实；可以关联分析，但**不能混成一个余额或财务账本**。
- 活动玩法和领取资格由业务决定；中台保留必要的防重、次数、额度与预算约束，不建通用营销规则引擎。

### 5.3 采购与供应额度

**经营首选：按需/按次向供应商采购或派发，不因未核销率低而主动建设囤券、库存或复杂采购优化机制。**

对 2026-10-22 羊毛/上力 Open API 的已知约束，须准确区分**预充值余额**与**发生扣减的时点**：

| 供应模式 | 已知扣减点 | 重要说明 |
| --- | --- | --- |
| A 礼包下单 | 创建已支付业务订单时扣礼包个数 | 用户后续进入 H5 完成适用的领取步骤 |
| B 腾讯出行直充 | 接口调用时扣礼包个数并尝试派发 | 要检查明细及 `allClaimed`，不能仅凭接口 `code=0` 认定全部到账 |
| C 公众号礼包券 | **签发时**预扣 `packCount` 个礼包 | 不是用户实际领取时才扣 |
| D 权益商品派发 | 提交派发时按成交价扣**权益余额（元）** | 要查询履约订单直到可靠终态；A/B/C 的礼包额度与 D 的金额余额是不同账 |

这不是已证实的「无需预充值的后付费」。**预算预留、上游扣额、实际履约、供应商是否退款/返额，必须分开记录**；未取得供应商确认前，不承诺过期未领自动返还额度。

具体防超支采用轻量措施：活动成本上限、用户/活动领取次数、供应商额度与价格限制、稳定业务单号和幂等。不建设庞大的预算审批/财务系统。

## 6. 一条能实际跑通的闭环

```text
下游业务确认激励条件 / 发起兑换
    → 核实用户映射、权益适用规则、活动额度
    → 留存业务意图及相应用户权益记录（依商品区分待履约/已交付）
    → 必要时经 Benefit Hub 调用供应商
    → 查证实际履约结果、同步用户权益状态
    → 记录实际供应成本与对应业务/活动
```

直接派发、需要用户后续领取、暂未使用等商品不强行采用同一状态转移路径。**发放请求成功、上游建单成功、用户确实到账是三件不同的事。**

出现网络超时或未知结果时：先查单，不能盲目换新单号重发；允许的原幂等键补发只在供应商明确支持的路径使用。第一阶段**不做自动跨供应商切换**；确认失败后依具体业务承诺和供应商条款处理补发、退款或积分返还，不伪造成功。

## 7. 经营指标：够用、可核实

建议先用以下五个口径形成轻量经营视图，**它们是管理建议，并非已上线统计功能**：

| 指标 | 建议口径 | 解释边界 |
| --- | --- | --- |
| 月有效权益用户 | 当月成功获得或使用权益的去重、可识别用户 | 不等同注册量；跨业务未确认关联不可强行去重 |
| 权益履约成功率 | 已确定结果的订单中，成功履约订单占比 | 同时披露处理中/未知订单，避免只选成功终态 |
| 跨业务有效转化 | 领取权益后在另一业务达成指定行为的关联用户及占比 | 先称「关联转化」；未经对照验证，不宣称全是权益带来的增量 |
| 单次有效权益成本 | 可核实的净采购成本 / 成功履约数量 | 口径须统一，退回、部分成功及待确认订单单列 |
| 权益活动净贡献 | 可归属收入 − 权益成本 − 其他直接成本 | 需要业务提供收入与成本事实；缺失则标「不可计算」，不编造收入 |

**优先证明**：真实用户激活、单位成本与履约可靠性、跨业务协同是否带来有经济意义的新增业务。不要把供应商标价、券面值或权益发放量当收入。

## 8. 不在当前阶段实施

- 全集团统一登录替换、复杂 CRM、全量用户画像；
- 统一福利商城/强制卡包前端；
- 泡泡值与学力值固定汇率、通用积分货币化或复杂清算；
- 通用用户转赠、转卖、二级交易市场；
- 自动智能比价/供应商切换、大库存采购引擎；
- 复杂财务结算、审批流、营销规则引擎、大数据 BI；
- 因战略规划而直接改动现有 Benefit Hub 的一期实施合同。

## 9. 后续需要验证，但不妨碍战略收口

1. 供应商真实商品和履约承诺是否可替换；哪些限制需要在目录显式表达。
2. A/B/C 的限领粒度、C 未领/过期是否返额、D 失败扣费和退款/撤销规则；供应商能力与风险以正式合同和联调结果为准。
3. 首批业务及商品、内部调用授权、预算不足/发放失败的用户提示与补偿方式。
4. 在跨业务身份明确关联后，数据授权及各业务提供最少经营事实的具体接口。
5. 数字权益模块何时作为独立工程范围启动；不能把「V1 战略确定」误写为「V1 已开发」。

## 10. 决策与实施状态

- **已确定的业务原则**：统一权益目录、轻量用户权益账户、权益默认可跨业务使用但可按商品限制；受控转赠由下游价值体系决定；公共福利池按活动显式授权、预算耗尽不自动兜底；按次/按需供给优先；权益、积分和广告收入分账。
- **战略建议但未冻结的实施选择**：首条闭环的具体 API 与状态结构、指标展示形式、备用供应商策略、具体期次切片。
- **本次不授权**：改代码、创建工程任务卡、创建 PR、上线/部署。
